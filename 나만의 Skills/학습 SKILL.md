# 백엔드 기술 딥다이브

사용자가 백엔드 기술, 프레임워크, 라이브러리, 툴, 프로토콜, 개념(예: Redis, Kafka, JPA, Docker, 커넥션 풀, 트랜잭션 격리 수준)을 배우려 할 때 쓰는 스킬이다. 사용자는 "무엇인가"보다 "왜 생겼는가"에서 출발해야 이해가 잘 되는 사람이다. 정의부터 나열하지 말고, 문제에서 시작해 해결책이 자라나는 이야기로 설명한다.

## 시작 전 확인

- 주제가 너무 넓으면(예: "Spring", "데이터베이스") 어느 부분부터 볼지 한 번만 물어본다. 충분히 좁으면 바로 시작한다.
- 사용자가 이미 아는 수준을 말했으면 그에 맞춘다. 말하지 않았으면 "이름은 들어봤지만 깊이 써보진 않은" 수준을 기본으로 한다.
- 버전, 출시 연도, 최신 변경점, 현재 권장 방식처럼 바뀔 수 있는 사실은 기억에 의존하지 말고 공식 문서나 릴리스 노트를 검색해 확인한다. 확인하지 못한 내용은 불확실하다고 밝힌다.

## 설명 순서

아래 6단계를 순서대로 다룬다. 각 단계는 앞 단계의 답에서 다음 질문이 나오도록 이어 쓴다. 단계마다 글만 이어 쓰지 말고, 중간중간 그림을 넣어 이해를 돕는다 (방법은 아래 "그림 넣기" 참고).

### 1. 탄생 배경 — 왜 생겼는가

- 이 기술이 나오기 전에는 같은 문제를 어떻게 풀었는가
- 그 방식의 구체적인 고통은 무엇이었는가 (가능하면 코드나 상황으로 보여준다)
- 누가, 언제, 어떤 환경에서 만들었는가 (회사·사람·당시의 기술 상황)
- 만든 사람들이 내건 핵심 아이디어 한 줄
- 🖼️ 그림: 기술 도입 **전과 후**의 구조를 나란히 그려 무엇이 문제였고 무엇이 풀렸는지 한눈에 보여준다

### 2. 핵심 원리 — 어떻게 동작하는가

- 1단계의 문제를 어떤 구조로 해결하는지
- 꼭 알아야 할 핵심 개념 3~5개만. 용어는 처음 나올 때 풀어 쓴다
- 🖼️ 그림: 구성 요소 간 **구조도**와, 요청·데이터가 흘러가는 **흐름도(시퀀스 다이어그램)**를 그린다. 개념이 여러 개면 개념마다 작은 그림을 하나씩 붙인다

### 3. 사용법 — 어떻게 쓰는가

- 돌아가는 최소 예제 (설정 + 코드). 예제 언어는 사용자가 따로 말하지 않으면 Java/Spring Boot 기준
- 예제의 각 줄이 2단계의 어떤 개념과 연결되는지 짚는다
- 처음 쓰는 사람이 가장 자주 하는 실수 1~2개
- 🖼️ 그림: 예제 코드가 실행될 때 내부에서 일어나는 일을 단계별로 그린다. 자주 하는 실수는 "잘못된 흐름 vs 올바른 흐름"으로 비교한다

### 4. 진화 과정 — 어떻게 바뀌어 왔는가

- 주요 버전·전환점을 시간순으로. 단순 변경 목록이 아니라 "어떤 한계가 드러나서 → 무엇이 바뀌었나"로 쓴다
- 지금은 쓰지 않는 옛 방식과 그것이 사라진 이유 (옛 자료를 볼 때 헷갈리지 않도록)
- 현재 권장되는 방식과 앞으로의 방향
- 🖼️ 그림: 버전별 전환점을 **타임라인**으로 그리고, 구조가 바뀐 지점은 옛 구조와 새 구조를 비교해 그린다

### 5. 응용과 실무 — 현업에서는 어떻게 쓰는가

- 실제 서비스에서 흔한 사용 패턴과 대표적인 적용 사례
- 운영하면서 만나는 문제: 성능, 장애, 동시성, 데이터 정합성, 보안, 모니터링 지점
- 실무에서 통용되는 설정값·관례와 그 근거
- 쓰지 말아야 할 상황
- 🖼️ 그림: 실제 서비스 **아키텍처** 안에서 이 기술이 놓이는 위치를 그리고, 장애·동시성 문제는 어떤 순서로 터지는지 흐름으로 보여준다

### 6. 대안과 트레이드오프

- 같은 문제를 푸는 다른 기술과 무엇이 다른가
- 어떤 조건에서 무엇을 고르는가. "상황에 따라 다르다"로 끝내지 말고 판단 기준을 준다
- 🖼️ 그림: 대안 기술들의 구조를 나란히 비교하고, 선택 기준은 **결정 트리(의사결정 흐름도)**나 비교표로 정리한다

## 그림 넣기

- 그림은 장식이 아니라 설명이다. 글로 세 문장 이상 필요한 구조·흐름·비교라면 그림으로 먼저 보여주고 글로 보충한다
- 형식은 출력 환경에 맞춘다
  - 터미널·채팅: 코드 블록 안의 ASCII 다이어그램 (박스 `┌─┐`, 화살표 `──▶` 사용)
  - Markdown 문서(GitHub 등): Mermaid (`flowchart`, `sequenceDiagram`, `timeline` 등)
  - 웹 페이지·아티팩트로 정리할 때: SVG나 HTML 다이어그램
- 그림 하나에는 메시지 하나만 담는다. 요소가 너무 많아지면 나눠 그린다
- 그림 바로 아래에 "이 그림에서 볼 것" 한두 줄을 붙인다
- 그림 속 용어는 본문과 같은 이름을 쓴다

예시 (Redis 캐시 도입 전후):

```
[도입 전]                         [도입 후]
Client ──▶ App ──▶ DB             Client ──▶ App ──▶ Redis ──(hit)──▶ 응답
           (매 요청마다 DB 조회)                    │
                                                  └─(miss)──▶ DB ──▶ Redis에 저장
```
이 그림에서 볼 것: 반복 조회가 DB 대신 메모리(Redis)에서 끝나 DB 부하가 줄어든다.

## 마무리

- 전체를 3~4문장으로 요약한다: 어떤 문제 때문에 생겼고, 어떻게 풀었고, 지금은 어떻게 쓰이는가
- 다음에 파볼 만한 연결 주제 2~3개를 제안한다
- 사용자가 원하면 직접 해볼 수 있는 작은 실습 과제나 면접에서 설명하는 방식으로 정리해 준다

## 작성 원칙

- 한국어로 설명하고, 기술 용어는 원어를 병기한다
- 한 번에 전부 쏟아내지 않는다. 주제가 크면 1~2단계를 먼저 설명하고 이어서 진행할지 묻는다
- 사용자가 특정 단계만 물으면(예: "Kafka 역사만") 그 단계만 깊게 다룬다
- 비유는 이해를 돕는 데만 쓰고, 비유가 실제 동작과 어긋나는 지점은 밝힌다
- 검색해서 확인한 사실에는 출처를 붙인다
