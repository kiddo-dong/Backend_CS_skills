# 백엔드 기술면접 통합 정리

두 자료의 면접 질문을 주제별로 합치고 중복을 없앤 뒤, 답변은 면접에서 말하기 좋은 길이로 새로 썼습니다. Java·Spring 백엔드 기준이라 Python과 Node.js 질문은 뺐습니다.

## 1. 네트워크·HTTP

- **브라우저에 URL을 입력하면 일어나는 일** — DNS로 도메인의 IP를 찾고, TCP 연결(HTTPS면 TLS 핸드셰이크까지)을 맺은 뒤 HTTP 요청을 보냅니다. 서버가 응답을 돌려주면 브라우저가 HTML을 파싱하고 CSS·JS·이미지를 추가로 받아 화면을 그립니다.
- **TCP와 UDP의 차이** — TCP는 연결을 맺고 순서 보장, 재전송, 흐름·혼잡 제어로 신뢰성을 보장합니다. UDP는 연결 없이 보내서 빠르지만 유실과 순서 뒤바뀜을 감수합니다. 스트리밍, 게임, DNS 조회처럼 속도가 중요한 곳에 UDP를 씁니다.
- **3-way / 4-way 핸드셰이크** — 연결은 SYN, SYN+ACK, ACK 세 번으로 양쪽의 송수신 가능 여부와 시퀀스 번호를 맞춥니다. 종료는 FIN, ACK, FIN, ACK 네 번인데, 상대가 아직 보낼 데이터가 남아 있을 수 있어서 ACK와 FIN이 분리됩니다.
- **OSI 7계층과 TCP/IP 4계층** — OSI는 물리, 데이터링크, 네트워크, 전송, 세션, 표현, 응용 계층입니다. 계층을 나누면 각 계층이 독립적으로 바뀔 수 있고 장애 지점을 좁히기 쉽습니다. TCP/IP는 이를 네트워크 접근, 인터넷, 전송, 응용 4계층으로 묶은 실제 구현 모델입니다.
- **웹 서버(Nginx, Apache)는 어느 계층에서 동작하는가** — HTTP를 다루므로 7계층(응용)입니다. URL 경로나 헤더를 보고 요청을 나누는 라우팅도 7계층 동작입니다. IP와 포트만 보고 나누는 L4 로드밸런서와 구분됩니다.
- **HTTP란** — 요청과 응답으로 이루어진 응용 계층 프로토콜이고, 무상태(stateless)라서 서버가 이전 요청을 기억하지 않습니다. 그래서 상태 유지를 위해 쿠키, 세션, 토큰을 씁니다.
- **HTTP 메서드** — GET(조회), POST(생성·처리), PUT(전체 교체), PATCH(부분 수정), DELETE(삭제)가 기본이고, HEAD와 OPTIONS는 각각 헤더만 조회, 지원 메서드 확인에 씁니다.
- **GET과 POST의 차이** — GET은 데이터를 쿼리 스트링에 담아 조회하고, 캐시와 북마크가 가능하며 멱등합니다. POST는 본문에 데이터를 담아 서버 상태를 바꾸고 멱등하지 않습니다.
- **멱등성** — 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질입니다. GET, PUT, DELETE는 멱등하고 POST와 PATCH는 보장되지 않습니다. 재시도 설계에서 중요합니다.
- **HTTP 상태 코드** — 2xx 성공(200, 201, 204), 3xx 리다이렉트(301, 302, 304), 4xx 클라이언트 오류(400, 401 미인증, 403 권한 없음, 404), 5xx 서버 오류(500, 502, 503)입니다.
- **HTTP/1.1, 2, 3의 차이** — 1.1은 연결당 요청을 순서대로 처리해 앞 요청이 막히면 뒤도 막힙니다(HOL 블로킹). 2는 한 연결에서 여러 스트림을 다중화하고 헤더를 압축합니다. 3은 TCP 대신 UDP 기반 QUIC을 써서 전송 계층의 HOL 블로킹과 연결 수립 지연을 줄였습니다.
- **HTTP와 HTTPS의 차이** — HTTPS는 HTTP에 TLS를 더해 암호화, 서버 인증, 무결성을 제공합니다. 기본 포트는 80과 443입니다.
- **TLS(SSL) 핸드셰이크** — 클라이언트와 서버가 지원 암호 방식을 교환하고, 서버가 인증서를 보내면 클라이언트가 CA의 공개키로 검증합니다. 이후 키 교환으로 세션키(대칭키)를 만들고, 실제 데이터는 그 대칭키로 암호화합니다. 비대칭키는 키 교환에만 쓰는 이유는 속도 때문입니다.
- **SSL Stripping** — 중간자가 HTTPS 연결을 HTTP로 낮춰 평문을 가로채는 공격입니다. HSTS 헤더로 브라우저가 항상 HTTPS만 쓰도록 강제해 막습니다.
- **URI, URL, URN** — URI는 자원을 식별하는 문자열 전체를 가리키는 상위 개념입니다. URL은 위치로 식별하고, URN은 위치와 무관한 이름으로 식별합니다.
- **REST와 RESTful** — 자원을 URI로 표현하고 행위를 HTTP 메서드로 나타내는 아키텍처 스타일입니다. 무상태, 캐시 가능, 일관된 인터페이스 같은 제약을 잘 지킨 API를 RESTful하다고 합니다. 장점은 직관적이고 HTTP 인프라를 그대로 쓴다는 점이고, 단점은 표준이 느슨하고 필요 이상의 데이터를 받거나 여러 번 호출해야 할 수 있다는 점입니다.
- **CORS와 해결 방법** — 브라우저는 출처(프로토콜, 호스트, 포트)가 다른 요청의 응답을 기본적으로 막습니다. 서버가 Access-Control-Allow-Origin 등의 헤더로 허용 출처를 알려주면 통과합니다. Spring에서는 @CrossOrigin, WebMvcConfigurer의 addCorsMappings, Spring Security의 CORS 설정으로 처리합니다.
- **캐시** — 자주 쓰는 데이터를 더 빠른 곳에 복사해 두는 것입니다. HTTP에서는 Cache-Control, ETag, Last-Modified로 브라우저와 CDN 캐시를 제어합니다.
- **JSON과 XML의 차이** — JSON은 키-값 구조로 가볍고 파싱이 빠릅니다. XML은 태그 기반으로 장황하지만 스키마 검증과 속성 표현이 풍부합니다.
- **MIME** — 전송하는 데이터의 형식을 나타내는 표준으로, Content-Type 헤더에 application/json, text/html처럼 씁니다.

## 2. 운영체제

- **프로세스와 스레드의 차이** — 프로세스는 독립된 메모리 공간을 가진 실행 단위이고, 스레드는 프로세스 안에서 코드, 데이터, 힙을 공유하며 스택만 따로 갖는 실행 흐름입니다. 스레드는 생성과 전환 비용이 적지만 공유 자원 때문에 동기화가 필요합니다.
- **PCB, PC, 캐시 메모리** — PCB는 운영체제가 프로세스마다 관리하는 정보 블록(상태, 레지스터, 메모리 정보)입니다. PC(프로그램 카운터)는 다음에 실행할 명령어 주소를 가리킵니다. 캐시 메모리는 CPU와 메인 메모리의 속도 차이를 줄이는 고속 저장소입니다.
- **컨텍스트 스위칭** — CPU가 실행 중인 작업의 상태를 PCB에 저장하고 다른 작업의 상태를 복원해 전환하는 과정입니다. 저장·복원과 캐시 무효화 비용이 들어서, 스레드가 지나치게 많으면 오히려 느려집니다.
- **동기·비동기, 블로킹·논블로킹** — 동기·비동기는 호출한 쪽이 결과를 직접 챙기느냐, 콜백이나 이벤트로 통지받느냐의 차이입니다. 블로킹·논블로킹은 호출한 스레드가 결과가 나올 때까지 멈추느냐의 차이입니다. 동기 블로킹은 단순하지만 스레드가 놀고, 비동기 논블로킹은 자원 효율이 좋지만 흐름 추적과 디버깅이 어렵습니다.
- **멀티스레드 프로그래밍** — 한 프로세스에서 여러 스레드로 작업을 동시에 처리하는 방식입니다. 응답성과 자원 활용이 좋아지지만 경쟁 상태, 교착상태, 컨텍스트 스위칭 비용을 관리해야 합니다.
- **Thread-safe의 의미와 설계법** — 여러 스레드가 동시에 접근해도 결과가 올바른 성질입니다. 공유 상태를 없애거나(지역 변수, 불변 객체), 락으로 임계 영역을 보호하거나, 원자적 연산(Atomic 클래스)과 동시성 컨렉션을 써서 만듭니다.
- **프로세스 동기화** — 공유 자원에 동시에 접근하는 임계 영역에서 데이터 일관성이 깨지지 않도록 실행 순서를 제어하는 것입니다. 상호 배제, 진행, 한정 대기를 만족해야 합니다.
- **세마포어와 뮤텍스의 차이** — 뮤텍스는 한 번에 하나만 들어갈 수 있는 락이고 잠근 스레드만 풀 수 있습니다. 세마포어는 카운터로 동시에 N개까지 허용하고, 다른 스레드가 신호를 줄 수 있습니다.
- **교착상태와 기아상태** — 교착상태는 서로가 가진 자원을 기다리며 영원히 멈춘 상태로, 상호 배제, 점유 대기, 비선점, 순환 대기 네 조건이 모두 성립할 때 생깁니다. 락 획득 순서를 통일하거나 타임아웃을 두어 조건 하나를 깨뜨립니다. 기아상태는 우선순위에 밀려 자원을 계속 못 받는 상태이고, 기다린 시간만큼 우선순위를 올리는 에이징으로 해결합니다.
- **가상 메모리** — 프로세스마다 독립된 주소 공간을 주고, 실제 필요한 페이지만 물리 메모리에 올리는 기법입니다. 물리 메모리보다 큰 프로그램을 실행할 수 있고, 없는 페이지에 접근하면 페이지 폴트가 발생해 디스크에서 가져옵니다.
- **캐시의 지역성** — 최근 접근한 데이터를 다시 쓰는 시간 지역성과, 인접한 주소를 이어서 쓰는 공간 지역성입니다. 캐시가 효과를 내는 근거이고, 배열 순회가 연결 리스트보다 빠른 이유이기도 합니다.

## 3. 데이터베이스

- **인덱스를 쓰는 이유와 장단점** — 인덱스는 컴럼 값을 정렬해 둔 별도 자료구조(보통 B+Tree)로, 전체 테이블을 훑지 않고 원하는 행을 찾게 해줍니다. 조회는 빨라지지만 저장 공간이 더 들고, INSERT·UPDATE·DELETE 때 인덱스도 갱신해야 해서 쓰기가 느려집니다. 선택도(카디널리티)가 높은 컴럼에 거는 것이 효과적입니다.
- **트랜잭션** — 모두 성공하거나 모두 취소되어야 하는 작업의 논리적 단위입니다. 계좌 이체에서 출금과 입금이 함께 반영되어야 하는 것이 대표 예입니다.
- **ACID** — 원자성(전부 또는 전무), 일관성(제약 조건을 항상 만족), 격리성(동시 트랜잭션이 서로 간섭하지 않음), 지속성(커밋된 결과는 장애가 나도 보존)입니다.
- **트랜잭션 격리 수준** — READ UNCOMMITTED(더티 리드 발생), READ COMMITTED(커밋된 것만 읽지만 반복 조회 시 값이 달라질 수 있음), REPEATABLE READ(같은 행은 같은 값이지만 팬텀 리드 가능), SERIALIZABLE(완전 격리, 성능 최저) 네 단계입니다. MySQL InnoDB의 기본값은 REPEATABLE READ, PostgreSQL과 Oracle은 READ COMMITTED입니다.
- **정규화** — 중복을 줄여 삽입·수정·삭제 이상을 막기 위해 테이블을 나누는 과정입니다. 1NF는 원자값, 2NF는 부분 함수 종속 제거, 3NF는 이행 함수 종속 제거입니다. 조인이 늘어 조회가 느려지면 일부러 반정규화하기도 합니다.
- **JOIN** — INNER JOIN은 양쪽에 모두 있는 행만, LEFT/RIGHT OUTER JOIN은 한쪽은 전부 포함하고 반대쪽이 없으면 NULL, FULL OUTER JOIN은 양쪽 전부, CROSS JOIN은 모든 조합을 반환합니다.
- **RDBMS와 NoSQL** — RDBMS는 고정 스키마와 조인, 트랜잭션으로 정합성이 중요한 데이터에 맞습니다. NoSQL은 스키마가 유연하고 수평 확장이 쉬워 대용량·비정형 데이터에 맞지만, 조인과 강한 일관성은 약한 경우가 많습니다.
- **CAP 이론과 Eventual Consistency** — 분산 시스템은 일관성, 가용성, 분할 내성을 동시에 모두 만족할 수 없습니다. 네트워크 분할은 피할 수 없으므로 실제로는 일관성과 가용성 중 하나를 고릅니다. Eventual Consistency는 가용성을 택하되 시간이 지나면 모든 노드가 같은 값으로 수렴한다는 모델입니다.
- **Redis** — 메모리 기반 키-값 저장소로 매우 빠르고, 문자열 외에 리스트, 해시, 셋, 정렬 셋 같은 자료구조를 지원합니다. 캐시, 세션 저장소, 분산 락, 랭킹, 메시지 브로커로 씁니다.
- **Redis와 Memcached의 차이** — Memcached는 문자열 키-값만 지원하는 단순한 멀티스레드 캐시입니다. Redis는 다양한 자료구조, 디스크 영속화(RDB, AOF), 복제와 클러스터, Pub/Sub을 제공합니다.
- **MongoDB** — JSON과 비슷한 문서(BSON) 단위로 저장하는 문서형 NoSQL입니다. 스키마가 유연하고 샤딩으로 수평 확장합니다.
- **Elasticsearch** — Lucene 기반의 분산 검색·분석 엔진입니다. 전문 검색, 로그 분석에 주로 씁니다.
- **Elasticsearch 인덱스와 RDBMS 인덱스의 차이** — RDBMS는 B+Tree로 값에서 행을 찾고, Elasticsearch는 역색인(단어에서 그 단어가 들어 있는 문서 목록으로 가는 구조)을 씁니다.
- **Elasticsearch 검색과 LIKE 검색의 차이** — LIKE '%단어%'는 인덱스를 못 타고 전체를 훑습니다. Elasticsearch는 형태소 분석으로 만든 역색인을 조회하므로 빠르고, 유사도 점수로 정렬할 수 있습니다.

## 4. 자료구조·알고리즘

- **시간 복잡도** — 입력 크기 n에 따라 연산 횟수가 어떻게 늘어나는지를 Big-O로 표현합니다. 상수와 낮은 차수는 버리고, O(1), O(log n), O(n), O(n log n), O(n²) 순으로 느려집니다.
- **배열과 연결 리스트의 차이** — 배열은 연속된 메모리라 인덱스 접근이 O(1)이지만 중간 삽입·삭제는 O(n)입니다. 연결 리스트는 노드를 포인터로 이어서 위치를 알면 삽입·삭제가 O(1)이지만 탐색은 O(n)입니다.
- **List와 Set의 차이** — List는 순서가 있고 중복을 허용합니다. Set은 중복을 허용하지 않고 구현에 따라 순서가 보장되지 않습니다.
- **해시 함수와 해시 테이블** — 해시 함수는 키를 고정 크기의 값으로 바꾸고, 해시 테이블은 그 값을 인덱스로 써서 평균 O(1)에 저장·조회합니다. 충돌은 체이닝(버킷에 리스트 연결)이나 개방 주소법(빈 칸 탐사)으로 해결합니다.
- **스택과 큐** — 스택은 나중에 넣은 것이 먼저 나오는 LIFO(함수 호출, 되돌리기), 큐는 먼저 넣은 것이 먼저 나오는 FIFO(작업 대기열, BFS)입니다.
- **힙과 우선순위 큐** — 힙은 부모가 자식보다 항상 크거나(최대 힙) 작은(최소 힙) 완전 이진 트리입니다. 삽입과 삭제가 O(log n), 최댓값·최솟값 조회가 O(1)이라 우선순위 큐의 구현체로 씁니다.
- **트리, 이진 트리, BST, AVL** — 트리는 사이클이 없는 계층 구조이고, 이진 트리는 자식이 최대 둘입니다. BST는 왼쪽 서브트리가 더 작고 오른쪽이 더 큰 이진 트리입니다. AVL은 좌우 높이 차를 1 이하로 유지하도록 회전하는 균형 BST입니다.
- **BST의 최악의 경우** — 정렬된 순서로 삽입하면 한쪽으로 치우쳐 연결 리스트처럼 되고, 탐색·삽입·삭제가 O(n)이 됩니다. 균형이 잡혀 있으면 O(log n)입니다.
- **피보나치 구현 방법** — 단순 재귀는 같은 계산을 반복해 O(2ⁿ)입니다. 메모이제이션이나 반복문(DP)으로 O(n), 직전 두 값만 들고 가면 공간도 O(1)로 줄일 수 있습니다.
- **DFS와 BFS** — DFS는 한 경로를 끝까지 들어가며 스택이나 재귀로 구현하고, 경로 존재 여부나 사이클 탐지에 씁니다. BFS는 가까운 노드부터 큐로 탐색하고, 가중치 없는 그래프의 최단 거리에 씁니다. 둘 다 O(V+E)입니다.
- **정렬과 탐색** — 버블·선택·삽입 정렬은 O(n²), 병합·힙 정렬은 O(n log n), 퀵 정렬은 평균 O(n log n)이고 최악 O(n²)입니다. 이진 탐색은 정렬된 데이터에서 범위를 절반씩 줄여 O(log n)에 찾습니다.

## 5. 보안·인증

- **대칭키와 비대칭키 암호화** — 대칭키는 같은 키로 암호화와 복호화를 해서 빠르지만 키를 안전하게 전달하기 어렵습니다(AES). 비대칭키는 공개키와 개인키 쌍을 써서 키 전달 문제가 없지만 느립니다(RSA). HTTPS는 비대칭키로 대칭키를 교환한 뒤 대칭키로 통신합니다.
- **단방향 암호화** — 해시처럼 원문으로 되돌릴 수 없는 변환입니다. 비밀번호 저장에 쓰며, 레인보우 테이블 공격을 막기 위해 솔트를 더하고 bcrypt처럼 일부러 느린 알고리즘을 씁니다.
- **쿠키** — 서버가 브라우저에 저장시키는 작은 데이터로, 이후 같은 도메인 요청에 자동으로 실려 갑니다. HttpOnly(JS 접근 차단), Secure(HTTPS만), SameSite(타 사이트 요청 제한) 속성으로 보호합니다.
- **세션의 개념과 동작 방식** — 로그인하면 서버가 사용자 상태를 저장하고 세션 ID를 발급해 쿠키로 내려줍니다. 이후 요청마다 세션 ID로 서버 저장소를 조회해 사용자를 식별합니다.
- **쿠키와 세션의 차이** — 쿠키는 클라이언트에, 세션은 서버에 저장합니다. 세션이 더 안전하지만 서버 메모리를 쓰고, 서버가 여러 대면 세션 공유(스티키 세션, Redis 같은 외부 저장소)가 필요합니다.
- **토큰 기반 인증** — 서버가 상태를 저장하지 않고, 서명된 토큰을 발급해 클라이언트가 요청마다 보내게 하는 방식입니다. 서버 확장이 쉽지만 발급한 토큰을 중간에 무효화하기 어렵습니다.
- **JWT와 그 구조** — Header(알고리즘), Payload(클레임), Signature(위변조 검증용 서명)를 Base64URL로 인코딩해 점으로 이은 토큰입니다. Payload는 암호화가 아니라 인코딩이라 민감 정보를 넣으면 안 됩니다.
- **JWT의 장단점과 보완책** — 서버 저장소 조회 없이 검증할 수 있어 확장에 유리합니다. 대신 탈취되면 만료 전까지 막기 어렵고 크기가 큽니다. 액세스 토큰 수명을 짧게 하고 리프레시 토큰으로 재발급하며, 필요하면 블랙리스트를 둡니다.
- **OAuth** — 사용자가 비밀번호를 넘기지 않고 제3자 앱에 제한된 권한을 위임하는 인가 프로토콜입니다. "구글로 로그인"이 대표 예입니다.
- **OAuth 아키텍처(구성 요소)** — 리소스 오너(사용자), 클라이언트(권한을 요청하는 앱), 서비스 제공자 세 가지이고, OAuth 2.0은 서비스 제공자를 인가 서버(토큰 발급)와 리소스 서버(API 제공)로 나눠 네 가지로 정의합니다. Authorization Code 방식은 사용자 동의 후 인가 코드를 받고, 서버가 그 코드를 액세스 토큰으로 교환해 API를 호출합니다.
- **JWT와 OAuth의 차이** — 비교 대상이 다릅니다. OAuth는 권한을 위임하는 절차(프로토콜)이고 JWT는 토큰의 형식입니다. OAuth의 액세스 토큰을 JWT 형식으로 발급하는 식으로 함께 쓰는 경우가 많습니다.
- **SQL Injection** — 입력값에 SQL 구문을 섞어 쿼리를 조작하는 공격입니다. 입력값을 문자열로 이어 붙이지 말고 PreparedStatement(파라미터 바인딩)를 써서 막습니다.
- **XSS** — 공격자가 심은 스크립트가 다른 사용자의 브라우저에서 실행되는 공격입니다. 출력 시 이스케이프, 입력 검증, CSP 헤더, HttpOnly 쿠키로 막습니다.
- **CSRF** — 로그인된 사용자의 브라우저가 자동으로 보내는 쿠키를 악용해, 사용자 모르게 요청을 보내게 하는 공격입니다. CSRF 토큰, SameSite 쿠키, Origin·Referer 검증으로 막습니다.

## 6. Java

### 객체지향

- **절차지향과 객체지향** — 절차지향은 실행 순서(함수 호출 흐름) 중심이라 단순하고 빠르지만, 규모가 커지면 수정 영향 범위를 파악하기 어렵습니다. 객체지향은 데이터와 행위를 객체로 묶고 객체 간 협력으로 구성해 재사용과 유지보수가 쉽지만, 설계 비용이 들고 상대적으로 무겁습니다.
- **객체지향의 4가지 특징** — 추상화(필요한 공통 특성만 뽑아냄), 캡슐화(내부 상태를 숨기고 메서드로만 접근), 상속(기존 클래스를 확장), 다형성(같은 타입으로 여러 구현을 다룸)입니다.
- **SOLID** — 단일 책임(클래스는 변경 이유가 하나), 개방-폐쇄(확장에는 열리고 수정에는 닫힘), 리스코프 치환(하위 타입은 상위 타입을 대체할 수 있어야 함), 인터페이스 분리(쓰지 않는 메서드에 의존하지 않게 잘게 나눔), 의존 역전(구현이 아니라 추상에 의존)입니다.
- **객체지향과 함수형의 차이** — 객체지향은 상태를 객체 안에 두고 메서드로 바꿉니다. 함수형은 불변 데이터와 부수 효과 없는 순수 함수를 조합해서, 동시성 환경에서 안전하고 테스트가 쉽습니다.
- **클래스와 객체** — 클래스는 설계도이고, 객체(인스턴스)는 그 설계도로 메모리에 만들어진 실체입니다.
- **인터페이스와 추상 클래스의 차이** — 추상 클래스는 상태(필드)와 일부 구현을 공유하는 "is-a" 관계이고 단일 상속만 됩니다. 인터페이스는 구현해야 할 기능의 규약이고 다중 구현이 됩니다. Java 8부터 인터페이스도 default 메서드를 가질 수 있습니다.
- **오버라이딩과 오버로딩** — 오버라이딩은 상위 클래스 메서드를 하위 클래스에서 재정의하는 것(런타임 다형성), 오버로딩은 같은 이름의 메서드를 매개변수를 달리해 여러 개 정의하는 것(컴파일 타임 결정)입니다.
- **강한 결합과 느슨한 결합** — 구체 클래스를 직접 생성해 쓰면 강한 결합이라 교체와 테스트가 어렵습니다. 인터페이스에 의존하고 외부에서 주입받으면 느슨한 결합이 됩니다.

### JVM과 메모리

- **JDK와 JRE의 차이** — JRE는 JVM과 표준 라이브러리로 이루어진 실행 환경이고, JDK는 JRE에 컴파일러(javac)와 개발 도구를 더한 것입니다.
- **JVM 구조와 Java 실행 과정** — javac가 소스를 바이트코드(.class)로 컴파일하면, 클래스 로더가 이를 메모리에 올리고, 실행 엔진이 인터프리터와 JIT 컴파일러로 기계어로 바꿔 실행합니다. JVM 덕분에 OS에 독립적입니다.
- **자바 메모리 구조** — 메서드 영역(클래스 정보, static 변수), 힙(객체와 배열, GC 대상), 스택(스레드별 지역 변수와 호출 프레임), PC 레지스터, 네이티브 메서드 스택으로 나뉩니다.
- **GC의 개념과 동작 방식** — 더 이상 참조되지 않는 객체를 자동으로 회수해 메모리 누수를 막습니다. GC 루트에서 도달 가능한 객체를 표시하고 나머지를 지우는 Mark and Sweep이 기본입니다. 힙을 Young과 Old로 나눠, 새 객체는 Young에서 자주(Minor GC), 오래 살아남은 객체는 Old에서 가끔(Major GC) 정리합니다. GC 중 애플리케이션이 멈추는 Stop-the-World를 줄이는 것이 튜닝의 핵심입니다.

### 문법과 타입

- **원시 타입과 바이트 크기** — byte 1, short 2, int 4, long 8, float 4, double 8, char 2바이트이고, boolean은 명세상 크기가 정해져 있지 않습니다.
- **원시 타입과 참조 타입의 차이** — 원시 타입은 값 자체를 스택에 저장하고 null이 될 수 없습니다. 참조 타입은 힙에 있는 객체의 주소를 저장합니다.
- **Wrapper 클래스** — 원시 타입을 객체로 감싼 클래스(Integer, Long 등)입니다. 컬렉션과 제네릭에 넣거나 null을 표현할 때 쓰고, 오토박싱·언박싱으로 자동 변환됩니다.
- **String을 ==로 비교했는데 같다고 나오는 이유** — String은 래퍼 클래스가 아니라 참조 타입입니다. 리터럴로 만든 문자열은 String Constant Pool에서 같은 객체를 공유하기 때문에 주소가 같습니다. new String()으로 만들면 다른 객체라 false가 나오므로 내용 비교는 equals를 써야 합니다.
- **동일성과 동등성** — 동일성(==)은 같은 객체(주소)인지, 동등성(equals)은 논리적으로 같은 값인지입니다. equals를 재정의하면 hashCode도 함께 재정의해야 해시 컬렉션에서 제대로 동작합니다.
- **String, StringBuilder, StringBuffer** — String은 불변이라 더할 때마다 새 객체가 생깁니다. StringBuilder는 가변이고 빠르지만 스레드에 안전하지 않고, StringBuffer는 동기화되어 안전하지만 더 느립니다.
- **Mutable과 Immutable 객체** — 불변 객체는 생성 후 상태가 바뀌지 않아 스레드에 안전하고 예측하기 쉽습니다. 필드를 final로 하고 setter를 없애며, 가변 필드는 방어적 복사를 해서 만듭니다.
- **static** — 인스턴스가 아니라 클래스에 속하는 멤버입니다. 클래스 로딩 시 한 번 만들어져 모든 인스턴스가 공유합니다.
- **final** — 변수에 붙이면 재할당 불가, 메서드에 붙이면 오버라이딩 불가, 클래스에 붙이면 상속 불가입니다.
- **지역 변수, 전역 변수, 정적 변수** — 지역 변수는 블록 안에서만 살고 스택에 저장됩니다. 인스턴스 변수는 객체와 함께 힙에 살고, 정적(static) 변수는 클래스가 로딩된 동안 유지됩니다.
- **접근 제어자와 쓰는 이유** — public(어디서나), protected(같은 패키지와 하위 클래스), default(같은 패키지), private(같은 클래스)입니다. 내부 구현을 숨겨 잘못된 사용을 막고 변경 영향을 줄이기 위해 씁니다.
- **제네릭** — 타입을 파라미터로 받아 컴파일 타임에 타입을 검사하고 형변환을 없애는 기능입니다. 런타임에는 타입 정보가 지워집니다(타입 소거).
- **애너테이션** — 코드에 붙이는 메타데이터로, 컴파일러 검사나 리플렉션을 통한 런타임 처리에 쓰입니다.
- **직렬화와 역직렬화** — 객체를 바이트 스트림으로 바꿔 저장하거나 전송하는 것이 직렬화, 다시 객체로 복원하는 것이 역직렬화입니다. Serializable을 구현하고, 제외할 필드는 transient를 붙입니다.

### 컬렉션

- **컬렉션 프레임워크** — List(순서, 중복 허용), Set(중복 불가), Queue(대기열), Map(키-값) 인터페이스와 그 구현체들입니다.
- **Vector와 ArrayList의 차이** — 둘 다 동적 배열이지만 Vector는 모든 메서드가 동기화되어 느립니다. 단일 스레드에서는 ArrayList를 씁니다.
- **HashSet, LinkedHashSet, TreeSet** — HashSet은 순서 없이 O(1), LinkedHashSet은 삽입 순서 유지, TreeSet은 정렬 상태를 유지하며 O(log n)입니다.
- **HashMap, LinkedHashMap, TreeMap, Hashtable** — HashMap은 순서 없고 null을 허용합니다. LinkedHashMap은 삽입 순서, TreeMap은 키 정렬 순서를 유지합니다. Hashtable은 동기화된 구형 클래스라, 멀티스레드에서는 ConcurrentHashMap을 씁니다.

### 예외, 동시성, 버전

- **Checked와 Unchecked Exception, 스프링 트랜잭션 롤백 대상** — Checked는 컴파일러가 처리를 강제하는 예외(IOException), Unchecked는 RuntimeException 계열입니다. @Transactional은 기본적으로 Unchecked 예외와 Error에서만 롤백하고, Checked까지 롤백하려면 rollbackFor를 지정합니다.
- **try-with-resources** — AutoCloseable을 구현한 자원을 try 괄호에 선언하면 블록이 끝날 때 자동으로 닫아줍니다. finally에서 직접 닫는 코드와 누수 위험이 사라집니다.
- **null을 안전하게 다루는 방법** — 반환값에 Optional을 쓰고, 빈 컬렉션을 반환하며, Objects.requireNonNull로 일찍 검증하고, @NonNull 같은 애너테이션으로 의도를 드러냅니다.
- **자바의 동시성 이슈** — 여러 스레드가 공유 변수를 동시에 읽고 쓰면 경쟁 상태로 값이 유실됩니다. synchronized나 ReentrantLock으로 임계 영역을 보호하고, volatile로 가시성을 보장하며, AtomicInteger와 ConcurrentHashMap 같은 동시성 클래스를 씁니다.
- **Java 8과 11의 주요 기능** — Java 8은 람다, 스트림 API, Optional, 인터페이스 default 메서드, 새 날짜·시간 API(java.time)를 도입했습니다. Java 11은 LTS로, 지역 변수 타입 추론 var(10에서 도입)의 람다 적용, 표준 HTTP Client, String 편의 메서드(isBlank, strip, lines)가 들어왔습니다.
- **스크립트 언어와 컴파일 언어의 차이** — 컴파일 언어는 실행 전에 전체를 기계어로 번역해 빠르고 오류를 미리 잡습니다. 스크립트 언어는 실행하면서 해석해 수정과 실행이 빠르지만 성능이 낮습니다. Java는 바이트코드로 컴파일한 뒤 JVM이 해석하고 JIT로 최적화하는 혼합 방식입니다.

## 7. Spring

### 핵심 개념

- **스프링이란** — 자바 엔터프라이즈 개발을 편하게 해주는 프레임워크로, IoC/DI, AOP, 추상화된 서비스(PSA)를 통해 객체 간 결합을 낮추고 비즈니스 로직에 집중하게 합니다.
- **프레임워크와 라이브러리의 차이** — 제어 흐름을 누가 쥐느냐의 차이입니다. 라이브러리는 내 코드가 호출하고, 프레임워크는 프레임워크가 내 코드를 호출합니다.
- **IoC와 DI, 동작 방식** — IoC는 객체 생성과 연결의 제어권을 개발자가 아닌 컨테이너가 갖는 것이고, DI는 그 구현 방식으로 필요한 의존 객체를 외부에서 넣어주는 것입니다. 컨테이너가 설정과 컴포넌트 스캔으로 빈 정의를 읽고, 빈을 생성한 뒤 의존 관계를 주입합니다.
- **IoC 컨테이너의 역할** — 빈의 생성, 의존성 주입, 생명주기 관리를 담당합니다. BeanFactory가 기본이고, ApplicationContext가 여기에 이벤트, 메시지, 환경 설정 기능을 더합니다.
- **Spring Bean이란** — IoC 컨테이너가 생성하고 관리하는 객체입니다.
- **Bean의 생성 과정(생명주기)** — 인스턴스 생성, 의존성 주입, 초기화 콜백(@PostConstruct), 사용, 소멸 전 콜백(@PreDestroy) 순입니다.
- **Bean의 Scope** — 기본은 컨테이너당 하나인 singleton이고, 요청할 때마다 새로 만드는 prototype, 웹 환경의 request, session, application이 있습니다.
- **DI의 종류** — 생성자 주입, 세터 주입, 필드 주입이 있고 생성자 주입을 권장합니다.
- **생성자 주입을 쓰는 이유** — 필드를 final로 선언해 불변을 보장하고, 의존성 누락을 객체 생성 시점에 잡으며, 순환 참조를 구동 시점에 발견하고, 스프링 없이도 테스트에서 직접 주입할 수 있습니다.
- **Autowiring 과정** — 먼저 타입으로 빈을 찾고, 같은 타입이 여러 개면 @Primary, @Qualifier, 필드·파라미터 이름 순으로 좁힙니다. 하나로 정해지지 않으면 예외가 납니다.
- **@Bean과 @Component의 차이** — @Component는 클래스에 붙여 컴포넌트 스캔으로 자동 등록합니다. @Bean은 @Configuration 클래스의 메서드에 붙여 반환 객체를 수동 등록하며, 외부 라이브러리 클래스를 빈으로 만들 때 씁니다.
- **POJO** — 특정 프레임워크의 클래스나 인터페이스에 종속되지 않은 순수 자바 객체입니다. 테스트와 재사용이 쉽습니다.
- **컨트롤러가 하나만 생성되는 이유** — 빈의 기본 스코프가 싱글톤이라 요청마다 객체를 만드는 비용을 없앱니다. 여러 스레드가 공유하므로 컨트롤러에 변경 가능한 상태를 두면 안 됩니다.
- **애플리케이션 구동 시 메서드를 실행하는 방법** — CommandLineRunner나 ApplicationRunner 구현, @PostConstruct, ApplicationReadyEvent를 받는 @EventListener를 씁니다.

### 웹 MVC

- **Servlet의 개념과 생명주기** — HTTP 요청을 받아 응답을 만드는 자바 클래스이고, 서블릿 컨테이너(톰캣)가 관리합니다. 최초 요청 때 init, 요청마다 service(doGet, doPost로 분기), 종료 때 destroy가 호출됩니다.
- **JSP, Servlet과의 차이** — JSP는 HTML 안에 자바 코드를 넣는 뷰 기술이고, 실행 시 서블릿으로 변환됩니다. 서블릿은 자바 코드 안에 HTML을 쓰므로 로직 처리에, JSP는 화면 표현에 맞습니다.
- **MVC 1과 MVC 2의 차이** — MVC 1은 JSP가 뷰와 컨트롤러를 모두 맡아 단순하지만 유지보수가 어렵습니다. MVC 2는 컨트롤러(서블릿)와 뷰(JSP)를 분리하며, 스프링 MVC가 이 구조입니다.
- **프론트 컨트롤러 패턴** — 모든 요청을 하나의 컨트롤러가 먼저 받아 공통 처리를 하고 알맞은 핸들러에 위임하는 구조입니다. 스프링에서는 DispatcherServlet이 그 역할입니다.
- **DispatcherServlet 동작 원리(스프링 MVC 흐름)** — 요청이 오면 HandlerMapping으로 처리할 컨트롤러를 찾고, HandlerAdapter를 통해 실행합니다. 컨트롤러가 뷰 이름을 반환하면 ViewResolver가 뷰를 찾아 렌더링하고, @ResponseBody나 @RestController면 HttpMessageConverter가 객체를 JSON으로 바꿔 응답합니다.
- **스프링이 서블릿을 구현한 방식, web.xml 역할 축소** — DispatcherServlet 자체가 HttpServlet을 상속한 서블릿 하나입니다. 예전에는 web.xml에 서블릿과 URL 매핑을 일일이 등록했지만, 지금은 DispatcherServlet 하나만 등록하고 매핑은 애너테이션으로 처리하며, 스프링 부트는 이 등록도 자동으로 합니다.
- **Filter와 Interceptor의 차이** — 필터는 서블릿 컨테이너 수준에서 DispatcherServlet 앞뒤에 동작하며 인코딩, 보안, 로깅처럼 스프링과 무관한 공통 처리에 씁니다. 인터셉터는 스프링 컨텍스트 안에서 컨트롤러 호출 전후에 동작하며, 핸들러 정보에 접근할 수 있어 인증·인가 확인에 씁니다.
- **Filter와 Interceptor의 예외 처리** — 인터셉터에서 난 예외는 DispatcherServlet 안이라 @ControllerAdvice로 처리됩니다. 필터에서 난 예외는 그 밖이라 @ControllerAdvice가 잡지 못하므로, 필터 안에서 직접 응답을 쓰거나 예외 처리용 필터를 앞단에 둡니다.

### AOP와 그 밖

- **AOP란, OOP와 비교** — 로깅, 트랜잭션, 보안처럼 여러 곳에 흩어지는 공통 관심사를 핵심 로직에서 분리하는 기법입니다. OOP가 책임을 객체 단위로 나눈다면, AOP는 OOP로 나누기 어려운 횡단 관심사를 모듈화해 보완합니다. 스프링은 프록시 객체로 구현합니다.
- **AOP 용어** — Aspect(공통 기능 모듈), Advice(실행할 공통 로직과 시점), JoinPoint(적용 가능한 지점), Pointcut(실제 적용할 지점을 고르는 표현식), Target(적용 대상 객체), Weaving(적용하는 과정)입니다.
- **스프링과 스프링 부트의 차이** — 스프링 부트는 자동 설정, starter 의존성 묶음, 내장 톰캣을 제공해 복잡한 XML·설정 없이 바로 실행 가능한 애플리케이션을 만들게 해줍니다.
- **대표 애너테이션** — @Component, @Service, @Repository, @Controller, @RestController(빈 등록), @Autowired(주입), @Configuration과 @Bean(설정), @RequestMapping과 @GetMapping(URL 매핑), @RequestBody, @PathVariable, @RequestParam(요청 데이터), @Transactional(트랜잭션)입니다.
- **Lombok 주요 애너테이션** — @Getter, @Setter, @NoArgsConstructor, @AllArgsConstructor, @RequiredArgsConstructor(final 필드 생성자, 생성자 주입에 사용), @Builder, @Data, @Slf4j입니다.
- **스프링 버전별 기능** — 3.0은 자바 기반 설정(@Configuration)과 REST 지원, 4.0은 Java 8 지원과 @RestController, 5.0은 리액티브 스택인 WebFlux를 도입했습니다. 6.0(부트 3)은 Java 17 이상과 Jakarta EE(jakarta 패키지)를 요구합니다.

## 8. JPA·데이터 접근

- **ORM** — 객체와 관계형 DB 테이블을 매핑해, SQL을 직접 쓰지 않고 객체로 데이터를 다루게 하는 기술입니다.
- **JPA와 Hibernate** — JPA는 자바 ORM의 표준 명세(인터페이스)이고, Hibernate는 그 대표 구현체입니다. Spring Data JPA는 그 위에서 리포지토리를 자동으로 만들어 주는 모듈입니다.
- **JPA를 쓰는 이유와 장단점** — 반복적인 CRUD SQL이 사라지고, 객체 중심으로 개발하며, DB 벤더에 덜 종속됩니다. 대신 학습 비용이 크고, 동작을 모르고 쓰면 N+1 같은 성능 문제가 생기며, 복잡한 통계 쿼리는 다루기 어렵습니다.
- **영속성 컨텍스트의 이점** — 엔티티를 보관하는 논리적 저장소입니다. 1차 캐시로 같은 트랜잭션 내 재조회를 줄이고, 같은 식별자면 같은 객체임을 보장하며, 쓰기 지연으로 SQL을 모아 보내고, 변경 감지(dirty checking)로 update를 자동 생성하며, 지연 로딩을 지원합니다.
- **N+1 문제** — 목록을 조회하는 쿼리 1번 뒤에, 각 행의 연관 엔티티를 가져오는 쿼리가 N번 더 나가는 문제입니다. 지연 로딩이든 즉시 로딩이든 발생합니다. fetch join, @EntityGraph, @BatchSize(default\_batch\_fetch\_size)로 해결합니다.
- **트랜잭션 전파(Propagation)** — 트랜잭션이 이미 있을 때 새 메서드가 어떻게 참여할지 정하는 옵션입니다. REQUIRED(기본값, 있으면 참여하고 없으면 생성), REQUIRES\_NEW(항상 새로 시작하고 기존 것은 보류), NESTED(세이브포인트로 중첩), SUPPORTS, MANDATORY, NOT\_SUPPORTED, NEVER가 있습니다.
- **MyBatis와 JPA의 차이** — MyBatis는 SQL을 직접 작성하고 결과를 객체에 매핑해 주는 SQL 매퍼라서, 복잡한 쿼리와 튜닝에 유리합니다. JPA는 SQL을 자동 생성하는 ORM이라 생산성과 유지보수에 유리합니다.
- **Spring JDBC** — JdbcTemplate으로 커넥션 획득, 예외 변환, 자원 해제 같은 JDBC의 반복 코드를 없애 줍니다. SQL은 직접 작성합니다.
- **DAO, DTO, VO** — DAO는 DB 접근 로직을 담는 객체, DTO는 계층 간 데이터 전달용 객체(로직 없음), VO는 값 자체를 표현하는 불변 객체로 값이 같으면 같은 객체로 봅니다.

## 9. 디자인 패턴

- **디자인 패턴이란** — 자주 만나는 설계 문제에 대한 검증된 해결 방식에 이름을 붙인 것입니다. 생성, 구조, 행위 패턴으로 나뉩니다.
- **싱글톤** — 인스턴스를 하나만 만들어 공유합니다. 자원을 아끼지만 전역 상태가 되어 테스트가 어렵고 멀티스레드에서 초기화에 주의해야 합니다. 스프링 빈이 대표 예입니다.
- **팩토리 메서드** — 객체 생성을 하위 클래스나 별도 메서드에 맡겨, 사용하는 쪽이 구체 클래스를 몰라도 되게 합니다.
- **빌더** — 매개변수가 많은 객체를 단계적으로 읽기 쉽게 생성합니다. 선택 값이 많을 때 생성자 오버로딩을 대체합니다.
- **전략** — 알고리즘을 인터페이스로 분리해 실행 중에 교체합니다. 결제 수단별 처리, Comparator가 예입니다.
- **상태(State)** — 상태를 객체로 만들어 상태에 따라 행동이 바뀌게 합니다. 상태가 많고 전이 규칙이 복잡해 조건문이 길어질 때(주문 상태, 자판기) 적합합니다. 상태 추가가 쉽고 조건문이 사라지지만 클래스 수가 늘어납니다. 전략 패턴과 구조는 비슷하지만, 상태 객체가 스스로 다음 상태로 전이한다는 점이 다릅니다.
- **템플릿 메서드** — 알고리즘의 뼈대는 상위 클래스에 두고, 달라지는 단계만 하위 클래스가 구현합니다.
- **옵저버** — 한 객체의 상태 변화를 구독한 객체들에게 자동으로 알립니다. 이벤트 리스너가 예입니다.
- **어댑터** — 호환되지 않는 인터페이스를 중간에서 변환해 함께 쓰게 합니다. 스프링의 HandlerAdapter가 예입니다.
- **브릿지(가교)** — 추상과 구현을 분리해 각각 독립적으로 확장할 수 있게 합니다. 상속 조합이 폭발하는 것을 막습니다.
- **퍼사드와 예시** — 복잡한 하위 시스템 앞에 단순한 창구를 둡니다. 여러 리포지토리와 외부 API 호출을 묶어 하나의 메서드로 제공하는 서비스 계층, SLF4J 같은 로깅 퍼사드가 예입니다.

## 10. 인프라·클라우드·DevOps

- **클라우드 컴퓨팅, AWS** — 서버, 스토리지, DB 같은 자원을 직접 구매하지 않고 인터넷으로 필요한 만큼 빌려 쓰는 방식입니다. AWS는 그 대표 사업자로 EC2(가상 서버), S3(오브젝트 저장소), RDS(관리형 DB) 등을 제공합니다.
- **IaaS, PaaS, SaaS** — IaaS는 인프라만 빌리고(EC2), PaaS는 실행 환경까지 제공받고, SaaS는 완성된 소프트웨어를 구독해 씁니다(Gmail, Slack).
- **서버리스** — 서버 관리를 클라우드에 맡기고 코드(함수)만 올려, 호출된 만큼만 과금되는 방식입니다. AWS Lambda가 예이고, 콜드 스타트 지연이 단점입니다.
- **스케일 업과 스케일 아웃** — 스케일 업은 서버 한 대의 사양을 올리는 것으로 단순하지만 한계와 단일 장애점이 있습니다. 스케일 아웃은 서버 대수를 늘리는 것으로 확장성과 가용성이 좋지만 로드 밸런싱과 상태 공유를 설계해야 합니다.
- **로드 밸런서** — 요청을 여러 서버에 나눠 보내고, 헬스 체크로 죽은 서버를 제외합니다. 라운드 로빈, 최소 연결, IP 해시 같은 방식이 있고, L4(IP·포트 기준)와 L7(URL·헤더 기준)로 나뉩니다.
- **리버스 프록시** — 클라이언트와 서버 사이에서 요청을 대신 받아 내부 서버로 전달하는 서버입니다. 내부 구조를 숨기고, TLS 종료, 캐싱, 로드 밸런싱을 맡습니다. Nginx가 대표적입니다.
- **고가용성과 Fault-tolerant 시스템** — 장애가 나도 서비스가 중단 없이 계속되는 성질입니다. 서버와 DB를 이중화하고 여러 가용 영역에 분산하며, 헬스 체크와 자동 장애 조치(failover), 오토 스케일링으로 단일 장애점을 없앤니다.
- **대용량 트래픽에서 장애 발생 시 대응** — 먼저 모니터링과 로그로 병목(CPU, 메모리, DB 커넥션, 느린 쿼리)을 찾습니다. 단기로는 스케일 아웃, 최근 배포 롤백, 유입 제한(rate limiting)으로 서비스를 복구합니다. 이후 캐시 도입, 쿼리와 인덱스 개선, 비동기 큐 처리, DB 읽기 분산, 서킷 브레이커로 재발을 막고 회고를 남깁니다.
- **MSA의 개념과 장단점** — 서비스를 기능 단위로 잘게 나눠 독립적으로 개발·배포하는 아키텍처입니다. 서비스별 확장과 배포, 장애 격리, 기술 선택의 자유가 장점입니다. 대신 서비스 간 통신과 분산 트랜잭션, 모니터링, 운영이 복잡해집니다.
- **컨테이너와 Docker, 왜 쓰는가** — 컨테이너는 애플리케이션과 실행 환경을 하나로 묶어 격리해 실행하는 기술이고, Docker는 그 대표 도구입니다. 호스트 OS의 커널을 공유해서 가상 머신보다 가볍고 빨리 뜹니다. 개발, 테스트, 운영 환경을 똑같이 맞출 수 있어 "내 컴퓨터에서는 되는데" 문제를 없앤니다.
- **컨테이너 환경에서의 디버깅** — docker logs로 로그를 보고, docker exec로 컨테이너 안에 들어가며, docker inspect와 stats로 설정과 자원을 확인합니다. 컨테이너가 금방 사라지고, 이미지에 디버깅 도구가 없으며, 로그가 흩어진다는 점이 어렵기 때문에 중앙 로그 수집이 필요합니다.
- **Kubernetes란, 왜 쓰는가** — 여러 서버에 걸쳐 컨테이너의 배포, 확장, 복구를 자동화하는 오케스트레이션 도구입니다. Docker가 컨테이너를 만들고 실행한다면, Kubernetes는 많은 컨테이너를 관리합니다.
- **Kubernetes 클러스터의 기본 아키텍처** — 컨트롤 플레인은 API 서버, etcd(상태 저장소), 스케줄러, 컨트롤러 매니저로 이루어집니다. 워커 노드에는 kubelet, kube-proxy, 컨테이너 런타임이 있고, 컨테이너는 파드 단위로 실행됩니다.
- **Kubernetes 오토 스케일링 원리** — HPA가 CPU·메모리 같은 메트릭을 주기적으로 보고 목표치에 맞게 파드 수를 조절합니다. VPA는 파드의 자원 할당량을, Cluster Autoscaler는 노드 수를 조절합니다.
- **모니터링 도구** — 시스템의 메트릭, 로그, 트레이스를 수집해 상태를 보여 주고 이상이 있으면 알립니다. Prometheus와 Grafana, ELK 스택, CloudWatch가 대표적입니다.
- **CI/CD와 장점** — CI는 코드를 자주 합치고 빌드와 테스트를 자동으로 돌리는 것, CD는 검증된 결과물을 자동으로 배포하는 것입니다. 통합 충돌을 일찍 찾고, 사람의 실수를 줄이며, 배포 주기를 짧게 만듭니다.
- **DevOps** — 개발과 운영의 경계를 허물고 자동화와 협업으로 빠르고 안정적으로 배포하려는 문화이자 방법론입니다.
- **RPC와 gRPC** — RPC는 원격 서버의 함수를 로컬 함수처럼 호출하는 방식입니다. gRPC는 구글이 만든 RPC 프레임워크로 HTTP/2와 protobuf를 써서 빠르고, 스트리밍을 지원하며, 서비스 간 내부 통신에 많이 씁니다.
- **protobuf** — .proto 파일에 스키마를 정의하고 바이너리로 직렬화하는 형식입니다. JSON보다 작고 빠르며 타입이 명확하지만, 사람이 읽을 수 없습니다.

## 11. 테스트·경험 질문

아래 질문은 정답이 없고 본인 경험으로 답해야 합니다. 테스트 관련 세 개만 기준이 되는 내용을 적었습니다.

- **테스트 코드에 대한 생각과 작성 방식** — 테스트는 리팩터링과 배포를 안심하고 할 수 있게 해주는 안전망입니다. 단위 테스트를 가장 많이, 통합 테스트를 그보다 적게 두고, given-when-then 구조로 한 테스트가 한 가지만 검증하게 작성합니다.
- **TDD** — 실패하는 테스트를 먼저 쓰고, 통과할 최소한의 코드를 작성한 뒤, 리팩터링하는 주기를 반복하는 개발 방식입니다. 설계가 테스트하기 쉬운 방향으로 잡히지만 초기 속도는 느려집니다.
- **테스트 커버리지에 대한 생각** — 커버리지는 테스트가 없는 곳을 찾는 지표이지 품질을 보장하는 수치가 아닙니다. 숫자를 채우는 것보다 핵심 비즈니스 로직과 경계 조건을 검증하는 것이 중요합니다.
